## 구조

매일 09:00 Claude 예약 하나가 사용자 컴퓨터에서 돈다.

1. `prepare`: 고정 스크립트가 최신 main을 받고 크롤러를 돌린다. AI가 아니다.
2. 자유 탐색: Titan 일반 채팅이 아는 사이트를 뺀 곳에서 공고를 찾는다(항목 14).
3. 조사와 작성: 웹을 읽는 하위 에이전트들이 조사하고, 주 실행이 `docs/daily-runbook.md` 2~7단계를 맞춘다.
4. `publish`: 고정 스크립트가 검사를 돌리고 캐시와 세 파일을 main에 바로 올리고, 공개 사이트 파일이 올린 파일과 같은지 확인한다.

GitHub은 보관, Pages, 지표 수집, 소스 수명주기, 상태 점검을 맡는다. 크롤러는 GitHub에서 돌지 않는다.

### 9. 고정 스크립트 `prepare`, `publish` [2, 3, 6, 7]

Windows에서 도는 Python이나 Node 스크립트다.

- `prepare`: 최신 main 받기, 의존성 확인(Python `tzdata` 포함), 크롤러 실행, 소스 실패와 끝까지 못 읽은 목록 보고, 필수 소스 실패면 중단. 기록은 `artifacts/daily/`에 남긴다(git에 올라가지 않는다): 그날 결과(`YYYY-MM-DD.json`), 시도별 단계·시간·오류·소스별 수치(`YYYY-MM-DD.log.jsonl`), 명령 전체 출력(`YYYY-MM-DD-이름.log`). 사용자 말: "로그같은거 잘 기록하게끔해. 디버깅/에러해결/개선작업 다 가능하게끔". 끝까지 못 읽은 목록 경고는 지금 `pipeline_health.mjs`에 있고 `crawl-sources.yml`에서 실행된다. 항목 12로 그 예약이 없어지므로 `prepare`가 직접 돌려야 한다.
- `prepare --no-pull`: main을 받지 않고 지금 코드로 돈다. 진행 순서 3단계 시험용이다. 브랜치를 바꾸지 않는다.
- `publish`: 최신 main 받기, 검사, 허용 파일 외 변경이면 거부, main에 푸시, 공개 파일 확인. 사람 계정 자격 증명으로 푸시하므로 Pages와 소스 수명주기 워크플로가 push로 시작된다(`pages.yml:3-9`, `evolve-crawler-sources.yml:3-7`).
- 검사는 승격 워크플로에서 옮긴다(`promote-daily-brief.yml:64-85`): 스냅샷 날짜가 오늘인지, main보다 예전 날짜가 아닌지, 날짜별 보관 파일과 조사 파일이 있는지, `latest.json`과 보관 파일이 같은지, `test_research_rules.py`, `test_publication_bundle.py`, `validate_data.py`, `validate_research_audit.py`. 마지막 검사에는 받은 main의 `latest.json`을 기준 자료로 준다.
- 공개 확인: 공개 사이트의 `data/latest.json`을 내려받아 올린 파일과 해시가 같으면 완료다. 같은 날 재시도도 이것으로 가린다. 푸시로 시작된 Pages는 날짜 검증을 건너뛰지만(`pages.yml:39-42`), 위 검사가 푸시 전에 끝나므로 Pages에 날짜를 넘기지 않는다. 기다리는 시간은 구현 때 Pages 실행 기록으로 정한다.
- 허용 파일은 5개다: `data/latest.json`, 오늘 날짜의 `data/archive/`와 `data/research/` 파일, 캐시 두 파일. `publish`는 이 5개만 `git add`하고, 추적 파일에 다른 변경이 있으면 거부한다. `.claude/` 같은 미추적 파일은 판정에 넣지 않는다.
- `promote-daily-brief.yml`을 지운다. `collect-github-metrics.yml`의 시작 조건은 이 워크플로 완료에 묶여 있어(`:3-7`), main의 `data/latest.json` 변경 push로 바꾼다.
- 같은 날 재시도를 허용한다. 지표 수집이 main에 올리는 시간과 겹치면 최신 main 위에 다시 얹어 푸시한다. 강제 푸시는 쓰지 않는다.

### 10. 쓰기 분리 [3]

main 보호는 하지 않는다. 혼자 보는 사이트라 검사를 통과하면 바로 공개한다. 웹을 읽는 일과 저장소에 쓰는 일만 나눈다. 웹 페이지의 글이 푸시로 이어지지 않게 하기 위해서다.

- 웹을 읽는 하위 에이전트는 Bash가 없는 전용 에이전트 정의로 만든다.
- 도구는 검색, 열람, 지정 폴더 쓰기, 브라우저 읽기로 제한한다. 예약 실행에서 지켜지는지는 구현 전에 시험한다.
- 원격 쓰기는 주 실행이 `publish`로만 한다.

### 11. 실행 환경 [2]

예약은 개발 폴더가 아니라 새로 복제한 전용 폴더에서 돈다. Claude 앱 예약 작업으로 매일 09:00에 시작한다. 프롬프트는 기존 문구의 1절을 위 구조로 바꾸고 2·3절은 8번과 main 직접 발행만 반영한다. 전날 실패의 잔여물은 `prepare`가 정리한다.

### 12. 고장 알림 [6, 7]

- `crawl-sources.yml`의 예약을 없애고 수동 실행만 남긴다.
- 알림은 오후 3시 GitHub 점검 메일 하나다(사용자 결정 "권고대로 반영"). 그날 공개 데이터가 오늘 날짜가 아니면 워크플로가 실패하고 GitHub 실패 알림 메일이 간다. 사용자 컴퓨터가 꺼진 날도 GitHub에서 돌기 때문에 잡힌다.
- 상태 점검은 발행 여부만 판정한다(2차 리뷰 발견 11). `pipeline_health.mjs:54-59`의 종료 판정에서 수집과 소스 조건을 뺀다. 수집 실패로 멈춘 날은 메일로 "발행 없음"이 오고, 원인은 `artifacts/daily/`의 그날 기록에서 찾는다.
- `pipeline_health.mjs:91`의 ChatGPT 문구를 Claude 예약과 로컬 기록을 보라는 문구로 바꾸고 `test_pipeline.mjs`의 기대값을 맞춘다.
- `pipeline-health.yml`은 첫 정상 발행 뒤에 다시 켠다. 기준을 오전 10시에서 오후 3시로 옮긴다(`pipeline_health.mjs:41,42`의 `hour<10`, cron).

### 13. 문서 [2]

`AUTOMATION.md`, `docs/data-pipeline.md`, `docs/daily-runbook.md`, `README.md`, `docs/README.md`의 ChatGPT 전제와 후보 브랜치 절차(`AUTOMATION.md:445-451,492-494`, `docs/daily-runbook.md` 9단계)를 구현과 함께 Claude 구조로 바꾼다. 복구 묶음 단계를 절차에서 뺀다. 구현 전까지 이 문서들은 옛 구조를 설명하며, 현재 기준은 이 설계 문서다.

### 14. 자유 탐색 [1]

아는 곳은 크롤러가, 나머지는 자유 탐색이 찾는다. 사용자 말: "어떤 워커한테는 우리가 이미 찾은곳제외 자유롭게 시키고 새롭게 알게되면 또 저장해놓고". 세부는 수집 설계 문서에 있다. 실행 주체는 Titan 일반 채팅으로 확정했다(사용자 결정 "권고대로 반영"). worker는 쓰지 않는다. 포털 순회 worker는 18분을 쓰고도 끝 페이지에 못 갔고, 일반 채팅은 조사 탭을 만들지 않았다(3차 기록). 그래서 worker 탭 정리는 이 전환의 선행 조건이 아니다.

다음이 필요하다.

- 이 프로젝트 전용 크롬. 사용자 말: "이 프로젝트 전용 크롬에다가 타이탄 플러그인 설치하고 gpt 로그인 해놓는게 좋겠다". 로그인은 사용자가 한다.
- 예약 시각에 Titan 앱과 전용 크롬이 켜져 있어야 한다.
- 네이버용 크롬과 동시에 켜 두면 안 된다. 새 채팅을 여는 API에는 브라우저를 고르는 값이 없고(`control-actions.ts` openChat), 먼저 받은 브라우저가 채팅을 맡는다(`bridge-custody.ts:128-139`). 동시에 켜야 하면 Titan에 브라우저 지정 기능을 넣는다.

## 테스트

목표 동작마다 하나다.

- 새 소스가 목록을 읽어 후보에 올린다 [1].
- 누락 측정이 모음 사이트 항목과 브리핑을 대조한다 [1].
- 접수 중 0건이어도 원본이 있으면 통과, 원본이 없으면 실패 [2].
- 재확인 실패는 사유가 있으면 통과, 사유가 없으면 실패 [2].
- `prepare`가 필수 소스 실패에서 멈추고 그날 기록에 사유를 남긴다 [6].
- `publish`가 허용 파일 외 추적 파일 변경을 거부하고 미추적 잔여물은 통과 [2].
- `publish`가 예전 날짜, 오늘이 아닌 날짜, 보관 파일 불일치, 검사 실패 때 푸시하지 않는다 [2].
- `publish`가 공개 파일이 다르면 실패로 끝난다 [2].
- 범위 밖 호스트 항목은 마감일이 모두 지나면 재확인 없이 CLOSED가 통과하고, 그 밖의 항목은 실패 [3, 4].
- `NOT_RELEVANT`에 사유가 없으면 실패 [1].
- 상태 점검이 발행 여부로만 실패한다 [6].
- Devpost 항목이 재확인 대상에서 빠지고 삭제는 계속 실패 [3, 4].

## 구현 전에 확인할 것

- 예약 작업이 승인 창에서 멈추지 않고 끝까지 도는지. 2026-11-04 시험 예약 생성은 자동 권한 판정에서 거부됐다. 사용자가 직접 만들어야 한다.
