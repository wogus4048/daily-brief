## 1. 발견

### F1. 목록 중간에서 한 쪽만 실패해도 소스 전체가 FAILED가 되어 읽은 자료가 사라진다
- 내용: `collectPaged`는 HTTP 비정상이면 throw한다. `gotoWithRetry`는 시간 초과만 한 번 재시도한다. throw는 `safeCrawl`이 잡아서 `count:0`, `items:[]`로 바꾼다. 이전에는 요청이 1~2번이었고 지금은 ContestKorea 분류별 약 70쪽을 이어서 읽는다. 실패할 기회가 몇십 배로 늘었다.
- 근거: `scripts/crawl_sources.mjs`의 `collectPaged`(HTTP 검사 줄), `safeCrawl`, `gotoWithRetry`. 모의 실험(`mock.mjs`)에서 분류 0의 5쪽만 503으로 답하게 했더니 `ContestKorea HTTP 503` throw가 나서 나머지 쪽의 자료도 전부 버려졌다.
- 등급: 코드와 모의 재현은 기록. 실서버에서 중간 쪽 오류가 실제로 얼마나 나는지는 모름(확인: 러너 로그 며칠치).
- 깨지는 목표: 1, 2("기존 매일 파이프라인을 깨지 않는다").
- 부가: `contestKorea`는 `required:false`라 실패해도 `validate_research_audit.py`가 FAILED 소스를 건너뛰고(약 213행) `hasUsableCache`도 통과한다. 하루치 ContestKorea 수집이 조용히 없어진다.
- 권고(근본): 쪽 단위로 재시도(5xx, 429, 시간 초과, 최대 2~3회)하고, 끝내 실패하면 throw하지 않고 읽은 것을 유지한 채 `coverage`에 `stoppedBy:"error"`, `reachedEnd:false`로 기록한다. 첫 쪽이 실패했을 때만 throw한다. 수정 위치는 `collectPaged` 한 곳(약 15줄)이다.

### F2. 빈 쪽을 "끝"으로 판정한다(차단 화면, 지연, 빈 응답이 끝으로 보인다)
- 내용: 0건인 쪽은 곧바로 `stoppedBy:"empty"`, `reachedEnd:true`가 된다. 봇 확인이나 빈 껍데기가 HTTP 200으로 와도 같다. 조사한 ContestKorea 목록은 200쪽 넘게 이어지는데 시작부터 끝까지 빈 쪽이 끝이 될 수 없다. 새 테스트(`test_crawl_navigation.mjs`)는 분류 2의 1쪽이 비어 있어도 `reachedEnd:true`를 기대하도록 고정해 놓았다.
- 근거: `collectPaged`의 `!rows.length` 분기. 모의 실험에서 분류 0의 5쪽을 "checking your browser" 200으로 답하게 했더니 `[5, true, "empty"]`로 기록됐고 15~16쪽의 접수 중 공고를 읽지 못했다.
- 등급: 코드와 모의 재현은 기록. 서버가 실제로 이런 응답을 주는지는 모름.
- 깨지는 목표: 1, 2("어디까지 읽었는지 기록")와 3(차단 우회 금지는 지키지만, 차단을 정상 종료로 기록한다).
- 권고: 빈 쪽을 끝으로 보는 것은 위비티처럼 서버가 끝을 알려주는 목록에만 허용한다. ContestKorea는 `minPages`나 "이전 쪽에 행이 있었는데 이번 쪽이 비면 한 번 다시 읽고 그래도 비면 `reachedEnd:false`, `stoppedBy:"blank"`"로 바꾼다. 분류 1쪽이 비면 0건이면 throw, 일부면 경고를 기록한다.

### F3. `reachedEnd:true`가 추정 정지에도 붙는다. 그리고 `coverage`를 읽는 코드가 하나도 없다
- 내용: `closedRun`(10쪽 연속 접수 중 없음)은 "끝"이 아니라 추정 정지인데 `reachedEnd:true`로 기록된다. `AUTOMATION.md:228`은 "`reachedEnd:false`는 쪽 한도로 잘렸다는 뜻"이라고만 쓴다. 또 `coverage`를 읽거나 경고를 내는 곳(`validate_research_audit.py`, `pipeline_health.mjs`, `crawl-sources.yml` 검증 단계, `evolve_crawler_sources.py`)은 코드에 한 줄도 없다. grep으로 확인했다.
- 근거: `collectPaged`의 `stoppedBy` 처리, 위 파일 grep 결과 일치 0건(문서와 캐시 제외).
- 등급: 기록(코드, grep).
- 깨지는 목표: 2("어디까지 읽었는지 기록"). 기록은 되지만 아무도 보지 않아 한도에 걸려도 아무 일도 안 생긴다.
- 권고: ① `closedRun` 정지는 `reachedEnd:false` 대신 `heuristicStop:true`처럼 따로 표기한다. ② 같은 `coverage`에 `lastOpenPage`와 `longestClosedRun`(읽은 중 가장 긴 접수 중 없는 구간)을 기록한다. 오늘 값은 29와 7이다. ③ `crawl-sources.yml` 검증 단계(Python 블록)에 `reachedEnd:false` 또는 `longestClosedRun >= 한계-2`이면 경고를 출력하는 두 줄을 넣는다.

### F4. 멈춤 기준 10쪽의 여유가 3쪽뿐이고, 표본이 하루치다
- 내용: 위 0번 표의 간격(7쪽)은 하루치다. 접수 기간이 긴 공고(상시 모집)가 한 건 더 있거나 없으면 간격이 커질 수 있다. 한계에 걸리면 먼 쪽의 접수 중 공고를 조용히 놓치고 F3 때문에 아무도 모른다.
- 근거: 0번 표.
- 등급: 간격 값은 기록. 다른 날의 간격은 모름(확인: 며칠간 같은 스캔을 남긴다. 위 `longestClosedRun` 기록이 그 일을 대신한다).
- 깨지는 목표: 1.
- 권고: 지금 값은 유지해도 되지만 F3의 `longestClosedRun` 기록 없이는 판단 근거가 쌓이지 않는다. 비용이 작으니 한계를 15쪽(분류당 약 5쪽, 전체 약 10~15초 추가)으로 올리는 것도 방법이다. 이 값을 어떻게 정할지는 아래 사용자 질문 1.

### F6. 같은 공고가 URL이 달라 중복으로 들어간다. ContestKorea와 위비티 모두
- 내용: ContestKorea는 한 공고가 두 분류 목록에 나오면 `Txt_bcode`가 달라 URL이 다르다. 오늘 98건 중 `str_no`가 같은 중복이 3건이다. 위비티 링크는 `gp`(쪽 번호)와 `cidx`(분류)를 품는다(실측 `?c=find&s=1&mode=ing&gub=1&cidx=1&gbn=view&gp=1&ix=111812`). 같은 공고가 분류마다 다른 URL이 되고(대경권 IR 5회), 날짜가 지나 쪽이 바뀌면 같은 공고의 URL이 매일 바뀐다. 검사기는 URL 문자열 그대로 비교한다(`research_rules.py`의 `normalize_url`은 호스트와 쿼리를 유지한다).
- 근거: 오늘 실행(`out.json`) 집계와 위비티 실측 href.
- 등급: 기록.
- 깨지는 목표: 3(매일 파이프라인). 지금은 ContestKorea에서만 영향이 있고(처분 3건 낭비), 위비티는 SHADOW라 검사기가 보지 않는다. 위비티를 정식 소스로 올릴 때 5배까지 처분이 늘 수 있다.
- 권고: 수집 시 공고 식별자(`str_no`, 위비티는 `ix`)로 합치고 URL은 대표형(`.../view.php?int_gbn=1&Txt_bcode=...&str_no=N`, `?c=find&gbn=view&ix=N`)으로 통일한다. `crawlerSpec`에 `idParam` 같은 필드를 두면 일반 소스에도 쓸 수 있다.

### F8. 사소한 어긋남
- 매니페스트 `contestKorea.url`은 아직 `https://contestkorea.kr/`인데 크롤러는 `www.contestkorea.com` 목록을 읽는다(`crawler-sources.json` 활성 항목). 기존 캐시에는 `.kr`과 호스트 없는 `.com` URL이 섞여 있다(11-02 캐시). 발행 데이터 `data/latest.json`의 공모전 61건에는 contestkorea URL이 하나도 없어서 호스트 변경이 발행 자료를 깨지 않는다(기록). 검사기가 호스트 문자열을 그대로 비교하므로 다음 감사 파일은 새 URL을 써야 한다. 등급: 기록. 깨지는 목표: 없음. 권고: 매니페스트 URL을 `.com`으로 맞춘다.
- `isActionableByHints`는 "예정" 부분 문자열을 힌트로 쓴다. 제목이나 설명에 "예정"이 들어간 마감 공고가 접수 중으로 판정될 수 있다(추정, 오늘 98건에서는 오탐을 못 찾음). 접수 예정 공고(예: D-113)는 접수 중으로 센다. 일관성은 있지만 `closedRun` 카운터를 되돌린다.
- 일반 소스에 `pagination`을 쓰면 `actionability:"all"`, `expand`, `scrollRounds`를 조용히 무시한다. `AUTOMATION.md:228`에는 이 제약이 없다.
- 테스트 빈틈: 중간 쪽 HTTP 오류, 200 빈 쪽, 분류 간 중복, `maxPages`에 걸린 ContestKorea는 시험이 없다. 새 시험의 기대값은 F2의 문제를 정답으로 고정하고 있다.

### 범위 밖(N)
- ContestKorea에 정렬 파라미터 `Txt_sortkey=a.int_sort` / `Txt_sortword=desc`가 있다(목록 폼의 input). 마감일순 정렬 값이 있는지는 확인하지 못했다(미확인, 읽기 전용으로 몇 번 시험하면 됨). 있다면 접수 중만 앞에 모이므로 휴리스틱이 필요 없다.

## 2. 문제없음으로 확인한 것
- 접수 중 판정(`D-\d+` 또는 힌트)은 D-0(오늘 마감)도 잡는다. 11월 5일 마감 공고를 "D-0 마감임박"으로 읽는 것을 실측했다.
- 심사중, 발표대기, 발표보기, 캠페인마감 행은 `isActionableByHints`에서 모두 제외됐다. "유료 접수" 꼬리말은 접수 중이 아니다.
- 사이드바의 광고 링크는 선택자(`.list_style_2`)가 제외한다. 위비티 `mode=ing`은 서버가 접수 중만 주고, 끝 쪽은 빈 행으로 확인된다.
- 소스 동시 실행: 활성 소스는 `Promise.all`로 각자 별도 페이지를 쓴다. ContestKorea 두 분류는 순서대로 읽는다. 위비티와 함께 돌려도 총 83초(내 실행)였다. 시간 초과 위험은 보이지 않는다(러너의 지연은 모름).
- 수명주기: `evolve_crawler_sources.py`의 `lastItemCount`, `lastActionableCount`는 값만 기록하고, `count`가 "접수 중만"으로 바뀐 것(54 → 98)이 점수나 강등 판정에 쓰이는 곳은 못 찾았다(코드 확인). 위비티가 FAILED여도 `hasUsableCache`의 shadow 검증은 통과한다.
- 차단 우회 금지(3): 새 코드에는 우회가 없고, 차단은 throw로 처리된다. F2는 "차단을 정상 종료로 기록한다"는 문제이지 우회가 아니다.

## 3. 더 나은 구조(제안, 근거는 코드와 실측)
1. 쪽 단위 재시도와 부분 결과 유지(F1), 빈 쪽 ≠ 끝(F2).
2. `coverage`에 `lastOpenPage`, `longestClosedRun`, `heuristicStop`을 기록하고 워크플로 검증 단계에서 경고를 출력(F3, F4). 이것이 "어디까지 읽었는지 기록"을 실제로 쓸모 있게 만든다.
3. 공고 식별자로 중복 제거와 대표 URL 통일(F6). 일반 소스용 `idParam`으로.
4. 정렬 파라미터가 마감순을 지원하면 휴리스틱 없이 해결(N).
