## B. 발견

### 발견 1. 처리 대상이 "약 128건"이 아니라 첫 실행에서는 그보다 훨씬 많다 (중요)

- 더해서 첫 발행은 10월 13일 이후 처음이라 재확인 대상이 다 쌓여 있다. main `latest.json`(date 2026-10-13)의 OPEN 44건이 2026-11-05 기준 전부 재확인 대상이다(`is_reverification_due`로 다시 계산, tzdata 없이 KST 고정으로 대체해 계산). Devpost 11건을 빼도 33건이다. 대부분 10월 13일 이후 마감일이 지난 항목이라 CLOSED 전환 근거 확인이 필요하다.
- 근거: 기록(`fullcrawl2` 캐시 합계 154, main `latest.json` 재집계 44/33), 코드(`validate_research_audit.py:197-234,323`).
- 깨지는 목표: 1, 8(3단계 시험이 "끝까지 잴 수 있는가"의 기준을 잘못 잡으면 8번의 확인이 헛돎).

### 발견 2. `prepare`가 main을 받는다는 점과 3단계(브랜치 시험)가 서로 어긋난다 (중요)

- 문제: 설계 9번은 `prepare`가 "최신 main을 받고" 크롤러를 돌린다고 쓴다. 3단계는 "`fix/crawler-resilience` 코드로 로컬에서 끝까지 1회"라고 쓴다. 지금 main의 `crawl_sources.mjs`는 콘테스트코리아 첫 화면만 읽고 위비티가 없으며(`git diff main fix/crawler-resilience --stat`: `crawl_sources.mjs` 212줄 변경, `data/crawler-sources.json` 53줄 변경), 항목 6~9의 구현도 main에 없다. 그대로 만든 `prepare`로는 3단계를 할 수 없다. `ref`(브랜치) 인자가 필요한데 설계에 없다.
- 더 큰 문제: 항목 6~9 코드와 `promote-daily-brief.yml` 수정이 main에 들어가기 전에는 실제 발행이 안 된다. 승격 워크플로는 후보 브랜치를 체크아웃해 거기 있는 `scripts/validate_research_audit.py`를 돌리고(`promote-daily-brief.yml:72`), 후보에 허용 경로 3개(캐시 포함 시 5개) 외 변경이 있으면 거부한다(`:95-103`, `git diff origin/main...HEAD`). 그래서 수정이 별도 브랜치에만 있으면 로컬 `publish`는 통과해도 GitHub 승격은 옛 검사기로 실패하거나 "forbidden path"로 거부된다. 설계 5번은 "`fix/crawler-resilience`를 합친다"만 적고 항목 6~9의 코드와 워크플로 수정이 언제 어떤 브랜치로 main에 들어가는지 적지 않았다.
- 근거: 코드(`promote-daily-brief.yml:40,72,95-103,113-124`).
- 깨지는 목표: 2(발행이 안 되면 완료 없음), 8(시험 순서가 서지 않음).
- 고치는 방법: `prepare --ref <branch>` 같은 인자를 정의하고, 진행 순서를 "2단계 구현 → 로컬 시험(브랜치) → 구현+크롤러 수정을 함께 main에 합침 → 실제 발행"으로 쓴다. 5단계 문구도 크롤러 브랜치만이 아니라 2단계 결과까지 합치는 것으로 고친다.

## D. 진행 순서가 정말 끝까지 도는가 (판정)

1. 승인 → 2. 구현 → 3. 시험 순서에서 "답이 없는 곳":
- `prepare`는 main을 받는데 시험 대상은 브랜치다(발견 2).
- 시험이 푸시 없이 끝나면 승격 워크플로(원격)의 반응은 한 번도 안 본다. 워크플로 수정(캐시 경로)은 5단계 첫 실제 발행에서 처음 실행된다. 첫 실제 발행 실패 시 main이 이미 합쳐진 상태다. 대안: 후보 브랜치를 `workflow_dispatch`(`candidate_ref`)로 한 번 시험하는 것은 main 합치기 뒤에야 가능하다(워크플로 파일은 main 기준). 이 위험은 설계에 적히지 않았다.
- 알림 경로(발견 6)와 처리량(발견 1)이 3단계 측정 항목에 빠져 있다.
- 4단계는 "후보를 더 거를지"를 정하지만 거르는 위치(크롤러 `actionability`)와 검사기의 154건 요구가 충돌한다. 거른 항목도 `actionableItems`에 남으면 처분이 필요하다. 어느 쪽에서 거르는지 설계에 없다.
