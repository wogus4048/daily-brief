리뷰어: Titan Web GPT 일반 채팅(대화 6aeb3f29-c588-83e8-a490-79867646b22a). 원문 그대로다.

독립 리뷰 결론: 현재 설계는 수정이 필요합니다. 세 차례의 채점 수치는 대체로 원본과 일치하지만, 실제 운영에서 목표 1·2·3을 달성하기에는 중요한 빈틈이 있습니다.
특히 다음 세 가지는 설계의 전제를 수정해야 할 정도로 중요합니다.

알고 있는 사이트의 수집 범위가 검증되지 않았습니다. 현재 크롤러는 ContestKorea 첫 화면만 읽고 페이지를 끝까지 순회하지 않습니다. 그런데 설계는 알려진 사이트를 자유 탐색에서 제외하려고 합니다.

새로 발견한 사이트가 자동으로 수집 대상이 되지는 않습니다. sourceDiscoveries는 후보 등록에 연결되지만, crawlerSpec 작성과 실제 수집 성공까지 이어지는 절차가 빠져 있습니다.

Titan 탭 정리의 수정 위치와 책임 범위가 불충분합니다. finish에는 브라우저 정리 호출이 없고, 탭 소유권은 확장 프로그램이 관리합니다. 종료 시점의 정리만 추가하면 일부 탭을 놓치거나 기존 사용자 탭에 영향을 줄 수 있습니다.

지정된 파일은 모두 읽었습니다. worker 생성, 브라우저 탭 조작, 파일 수정은 하지 않았습니다.

3. 더 나은 구조 제안
현재 설계의 장점은 크롤러, 자유 탐색, 공식 확인을 나눴다는 점입니다. 다만 역할을 수집 주체 기준으로만 나누면 크롤러가 놓친 부분을 자유 탐색이 보완하기 어렵습니다.
다음 구조를 권합니다.
권장 데이터 흐름. 크롤러가 못 읽은 범위도 탐색 대상으로 남기고, 모든 공고는 같은 후보 원장에서 검증합니다.
차이는 세 가지입니다.
첫째, 출처를 ACTIVE냐 아니냐로만 나누지 않고, 어느 범위까지 수집됐는지 관리합니다. 예를 들어 위비티의 IT 분야 1~2페이지는 수집됐지만 기획 분야는 일부 실패했다면, 자유 탐색이 그 부분을 보완할 수 있어야 합니다.
둘째, 후보 원장을 공통으로 둡니다. 크롤러에서 가져온 공고, 검색으로 찾은 공고, worker가 보고한 공고를 모두 제목·URL·수집 경로·확인 상태와 함께 합칩니다. 이미 수집한 항목이라도 공식 확인이나 변경 여부를 다시 조사할 수 있습니다.
셋째, 새 출처의 발견과 실제 채택을 분리합니다. 발견한 목록을 먼저 보존하고, 크롤러 명세가 준비되지 않은 사이트도 사람 또는 에이전트가 점검할 수 있게 유지합니다. 이 방식은 현재의 NEEDS_SPEC → SHADOW → ACTIVE 수명주기를 그대로 활용할 수 있습니다.
탭 정리는 Daily Brief 설계와 별도로 Titan에서 해결하는 것이 적절하지만, Daily Brief의 실행 주체가 Claude가 되더라도 실제 브라우저 탭이 생성되는 경로는 확인해야 합니다. worker를 쓰지 않는다는 사실만으로 탭이 생성되지 않는다고 단정할 수는 없습니다.
4. 사용자 결정이 필요한 질문
다음은 기술적 사실만으로 대신 결정하면 안 되는 부분입니다.

자유 탐색의 우선순위: 이미 수집한 사이트에서도 누락을 줄이기 위해 자유 탐색이 다시 조사하도록 허용할까요? 저는 사이트 전체 제외보다 미수집 범위 중심의 보완을 권합니다.

실행 주체: Claude와 Titan의 동일 조건 비교를 한 뒤 신규 공식 확인 건수와 운영 안정성을 기준으로 선택할까요? 현재 기록만으로 한쪽을 확정하기는 어렵습니다.

실패한 날의 발행: 자유 탐색이 실패해도 정상 브리핑을 발행할지, 수집이 불완전했다는 표시를 남기며 발행할지 결정이 필요합니다. 저는 발행은 허용하되 조사 상태를 남기는 쪽을 권합니다.

Titan 탭 정리 정책: worker가 직접 생성한 탭은 종료할 때 자동으로 닫는 것을 기본값으로 할까요? 저는 생성 기록이 확실한 탭에 한해서 자동 정리하는 정책을 권합니다.
