## 냉정 리뷰 결론

설계대로 해도 시험은 통과하지 않는다. DACON 판정만 고치면 `validate_research_audit.py:498`에서 재확인 실패 12건으로 막히고, `scopeRemovals`는 270행만 고쳐서는 Devpost 항목도 풀지 못한다. 리뷰어는 DACON만 완화한 사본으로 시험 산출물을 실제 실행해 확인했다.

## 냉정 리뷰 발견

1. 재확인 실패는 사유를 적어도 발행을 막는다(`:497-501`, `:503-508`). 런북 53행과 코드가 다르다. 지금까지 발행 기록 4개는 실패가 0건이라 드러나지 않았다. 깨지는 목표 1. 제안: `failed_ids` 제외(2줄), 규칙은 사용자가 정한다.
2. `scopeRemovals`는 동작하지 않고 프롬프트의 누적 자료 보존과 충돌한다(`:317-324`는 기준선에서 대상을 계산). 깨지는 목표 1, 2, 3. 제안: 항목을 지우지 말고 `research_rules.py`의 `is_reverification_due`에서 범위 밖 호스트를 제외한다.
3. Devpost 항목은 10건이 아니라 11건이다(`galuxium-nexus-v2-2026` 포함). 깨지는 목표 3.
4. 쓰기 분리는 선언일 뿐이다. main 보호와 ruleset이 없고 같은 자격 증명을 쓴다. `prepare`의 main 푸시와 main 보호는 양립하지 않는다. 깨지는 목표 2. 제안: 캐시를 후보 브랜치에 싣고(`promote-daily-brief.yml:100,120,129`), main에 ruleset을 건다.
5. 상태 점검을 켜면 늦게 발행된 날에도 실패 메일이 온다(`pipeline_health.mjs`의 `hour<10`, 점검은 예약보다 크게 늦음). 깨지는 목표 5. 제안: 기준 시각과 cron을 맞춘다.
6. 한국만 수집하면 트랙 최소 후보 수(`aiData` 10, `generalSoftware` 15)와 맞지 않는다. 시험일 기준 각각 9, 12(호스트 기준 추정 포함). 깨지는 목표 3.
7. `crawl-sources.yml` 예약을 없애면 크롤러 테스트 4종의 자동 실행, 발행 없는 날의 지표 갱신, 실패 진단 산출물이 빠진다. 깨지는 목표 없음.
8. 같은 날 재시도 때 후보 브랜치 푸시가 거부될 수 있다. 깨지는 목표 1. 제안: 원격 브랜치 위에 커밋을 얹어 fast-forward로 푸시한다.
9. 복구 묶음 단계는 빼도 된다. `publish`가 같은 검증을 돌린다. 깨지는 목표 없음.
10. 전용 폴더, 하위 에이전트 분담, 8절은 사용자 목표 번호를 붙일 수 없다. 깨지는 목표 없음.
11. DACON 0건 판정 수정은 타당하다. 다만 카드 문구가 바뀌어 추출이 고장 난 날과 구분하지 못한다. 지금도 같다. 깨지는 목표 없음.

## 구현자 점검 질문

1. 예약 실행 방식과 승인 없이 끝까지 도는지.
2. `prepare`의 main 푸시가 허용되는지, 무인 자격 증명이 되는지.
3. 고장 알림 여부와 점검 시각.
4. `Devpost/Meetup` 항목 처리, "원본 있음"의 기준.
5. `scopeRemovals`의 안전 범위와 다른 해외 항목 소급 여부.
6. 전용 폴더를 clone으로 할지 worktree로 할지, 의존성 설치 주체.
7. 일주일 관찰을 계획에 넣는지.
8. 프롬프트 원문이 `docs/chatgpt-task-prompt.txt`와 같은지.
